# 새 세션의 표준 실행 경로

이 문서와 공용 코드를 기준으로 실행한다. 이전 대화·개인 보고서·앱 캐시는 필요하지 않다. 브라우저 연결·모델 선택은 현재 환경의 도구 문서와 사이트별 지침을 따르며, 아래의 측정·저장·출력 코드는 새로 만들지 않는다.

## 0. 준비

1. [설정·명령 참고의 시작](RUNBOOK.md#시작)과 `config/benchmark.json`, `cases/core.json`을 확인합니다. 이번 사용자의 모델·질문·요청 범위와 첨부 검토 결과를 로컬 설정에 반영합니다. 개발용 smoke와 최종 core 결과는 섞지 않습니다.
2. [측정 규약](PROTOCOL.md)과 [평가 기준](EVALUATION.md)을 읽습니다. 추론만 불일치하면 [추론 예외 정책](EXECUTION-RELIABILITY.md)을 따릅니다. ChatGPT의 Chat/Work 사용 모드도 고정·기록합니다.
3. [브라우저 체크리스트](BROWSER-FLOW.md)와 그 문서에 연결된 대상 사이트 지침을 실제 조작 전에 읽습니다. 현재 도구·로그인·모델 지원을 확인하며 과거 계정의 설정을 재사용하지 않습니다.
   첫 전송 전에 메모리·개인화·검색 등 비교에 영향을 주는 설정과 원상복구할 값을 로컬에 기록합니다. 변경이 필요하면 이번 실행의 승인 범위를 확인합니다. 메뉴/첨부 확인 실패의 복구는 BROWSER-FLOW를 따르며, 다른 확정 묶음까지 불필요하게 중단하지 않습니다.
4. `init --config local/실행설정.json --cases local/질문설정.json`으로 승인된 계획을 날짜 없는 새 run ID에 고정합니다. 실행 도중 계획을 소급 변경하지 않습니다. 원화 환산율은 사용자 입력으로 받고 이미 제공한 정보는 반복해서 묻지 않습니다.

아래가 기본 실행 순서입니다. RUNBOOK은 명령·필드 참고, BROWSER-FLOW는 UI 확인, EXECUTION-RELIABILITY는 추론 예외·선택적 보조 코드 참고입니다. STATUS의 과거 검증 기록은 이번 실행의 승인이나 실측 결과가 아닙니다.

## 1. 역할을 고정한다

| 역할 | 담당 |
|---|---|
| 로그인, 모델·추론·입력 확인, 전송, 완료 UI 확인 | 연결된 브라우저 도구를 사용하는 에이전트 |
| 시작/완료 시계와 결과 연결 | `benchmark timer-*`, `record` |
| 답변 평가·서비스 간 해설 | 실제 원문을 읽는 에이전트 + EVALUATION 기준 + 아래 예시 |
| 누락 점검 | `benchmark audit` |
| PDF·엑셀·모델별 선그래프 | 기존 `benchmark report` 한 경로 |

`record_ui.py` 등 별도 측정/저장 프로그램, 새 보고서 빌더를 실행 때마다 만들지 않는다. 도구 API가 다르면 **UI 조작 부분만** 바꾼다. 연결된 도구의 허용 API 밖에서 브라우저를 제어하지 않는다. 이 키트가 브라우저 인증·완료 여부를 자동 판정하는 것은 아니다.

## 2. 모든 실제 요청에서 반복하는 순서

위 준비를 완료한 뒤 [상태 기록 명령](RUNBOOK.md#상태-기록-명령)의 이벤트 필드를 참고한다. `pilot`과 `mono-summary`는 예시이므로 실제 run/request ID로 바꾼다.

1. 새 대화·모델·추론·첨부·질문 원문을 확인하고 입력을 완료한다. 잔액을 확인하고 전송 버튼까지 준비한다.
2. reserve를 저장한다. 이후 아래 명령이 성공해야 클릭한다.

```sh
python3 -m benchmark timer-start --run pilot --request mono-summary --evidence "현재 새 대화의 모델·추론·입력과 전송 버튼 확인"
```

3. **곧바로** 승인된 질문을 UI에서 한 번만 전송한다. 다른 사이트 설정이나 문서 작성으로 넘어가지 않는다. 클릭 오류/타임아웃이면 대화와 사용량을 확인하며 전송을 반복하지 않는다. 시작 명령을 다시 실행해 시계를 초기화하지 않는다.
4. 현재 요청의 입력과 답변을 연결해 관측한다. 오래 걸리면 30초 이내 관측 창으로 이어가며 진행 상황을 알린다. REPL 변수가 없어져도 시계는 `runs/<id>/session.json`에 남는다. `status`로 확인하고 관측만 재개한다.
5. 현재 답변이 끝났다는 UI 신호와 마지막 문장을 확인한 **직후**, 원문 추출·비용 확인·채점 **전에** 실행한다.

```sh
python3 -m benchmark timer-complete --run pilot --request mono-summary --evidence "현재 질문의 답변 끝 문장과 완료/복사 버튼 확인; 생성 중 표시 없음"
```

6. 원문을 저장한다. 코드 블록·표·캔버스가 화면 텍스트 추출에서 비었다면 UI/지원되는 복사 기능으로 대조한다. 모델 답변의 결함과 추출 도구의 누락을 구분한다. 확인했다면 result에 `answer_capture_verified:true`, `capture_evidence`를 기록한다. 못 확인했다면 false와 limitations를 남기며, 빈 코드 블록을 곧바로 모델의 0점 답변으로 취급하지 않는다.
7. 비용을 대조한 뒤 기존 `record --event ...result.json`을 사용한다. 시간 필드는 직접 계산·복사하지 않는다. 저장된 시계가 자동 병합되며 null로 덮어쓸 수 없다. 수동 숫자가 충돌하면 해당 숫자를 제거하고 저장된 원기록을 확인한다.
8. **매 요청** `status`의 시간 누락과 pending을 확인한다. 누락 시 답변은 보존하며 유료 재전송하지 않는다. 다음 요청 전에 타이머 명령 연결을 바로잡는다.

이 경로는 외부 도구 호출·저장 오버헤드가 포함된 **완료 관측 상한 `≤N초`**다. 생성 중 화면을 본 뒤 기록한 시각은 화면 획득 시각과 다를 수 있어 하한으로 만들지 않는다. 정밀 서버 생성시간이라고 쓰지 않는다. 긴 중단 뒤 완료를 확인했다면 넓은 상한임을 limitations에 쓰고 속도 우열을 단정하지 않는다. 시계가 불일치하면 원값은 남기고 시간을 미관측으로 표시한다.

기존 Playwright 환경의 `browser/observe.mjs`는 [선택적 대체 경로](EXECUTION-RELIABILITY.md)다. 동일 요청에서 두 측정 경로를 혼용하지 않는다. 새 세션의 기본은 위 영속 CLI 경로이며, 이를 사용할 수 없는 환경은 임의 타이머를 만들어 유료 테스트를 시작하기 전에 제약을 알린다.

## 3. 원하는 보고서 수준을 기록으로 고정한다

`examples/review-example.json`은 **실측이 아닌 가상 예시**다. 구조와 근거 수준만 참고하고 문구·점수·답변을 실제 결과로 복사하지 않는다.

- assessment: 5개 기준별 관찰·점수 이유·위치에 더해 `summary`의 `strength`, `weakness`, `practical_impact`, `evidence_ref`를 작성한다. 각 항목 1~2문장, 전체 200~350자 정도를 권장한다. 억지로 단점을 만들지 않고 '확인한 범위에서는 누락 없음'이라고 쓸 수 있다.
- comparison: 같은 모델·질문의 **모든 측정 서비스**를 observations에 넣는다. `conclusion` 외에 `common_ground`, `differences`, `practical_impact`를 구분한다. 동점이면 점수 차이를 만들지 않고 실제 접근법·필요한 편집을 설명한다. 유의미한 차이가 없다면 없다고 쓴다.
- UX는 점수와 분리해 서비스별 실제 메뉴/설정 유지/첨부/비용 확인/가독성을 기록한다. 측정하지 않은 클릭 횟수를 지어내지 않는다.
- summary/해설은 기존 PDF·엑셀 빌더가 직접 출력한다. 새 템플릿을 작성하지 않는다.

## 4. 생성과 완료를 구분한다

```sh
python3 -m benchmark audit --run pilot
python3 -m benchmark report --run pilot --rates local/credit-rates.json
```

audit는 결제 차단이나 재시도 명령이 아니다. 평가·총평·비교 해설 누락은 저장된 원문으로 보완한다. 평가를 이미 기록했다면 새 assessment/comparison에 최신 이벤트의 `supersedes_sequence`와 `revision_reason`을 넣어 정정한다. 원본 이력은 남고 출력은 최신 평가를 쓴다. 실제 관측하지 않은 시각이나 비용은 만들지 않는다. 측정 중 수동 정정으로 시간을 소급 입력하지 않는다.

`record_checks_passed`는 필드·범위 점검이지 평가 내용의 진실성이나 시각 품질 보증이 아니다. `review_needed`여도 보고서는 출력하며 첫머리에 미완료 항목을 보여준다. report의 `review.issues`를 확인해 남은 문제를 최종 답변에 알린다.

전달 전 확인:

- GPT·Claude·Gemini의 예정/기록 수 및 미실행 사유. 전체 기본 범위는 40회이며 GPT만 완료하면 전체 완료가 아니다. 모델 없음·조건 미확정·미실측·도구 한도를 구분하며 하나의 실패나 0점으로 합치지 않는다.
- 성공 답변 수와 시간 관측 수. 시간 누락 0건인지 확인하되 실패를 숨기거나 재전송해 숫자를 맞추지 않는다.
- 상세 PDF: 모델별 요약, 구체적인 서비스 차이, 각 답변의 강점·한계·실무 영향·5개 근거, UX.
- 엑셀: 모델별 요약/서비스 비교/기준별 평가/실측 원장/답변 원문/사용 경험 6개 시트, 정확한 모델명·추론·KRW·시간 표시. 비교표의 MonoGPT·Timely AI·ChatGPT 열은 유지하고 미지원 칸은 모델 없음으로 둔다. 질문은 한 번씩 수록하고 서비스별 답변은 질문 ID로 연결한다.
- 그래프 PDF: 범위표, 각 실측 모델의 비용·품질 선그래프, 별도 시간 선그래프·수치 대조. 미지원/미측정은 0이 아니라 빈 지점과 설명.
- PDF 렌더와 엑셀 화면에서 잘림·겹침·한글 글꼴·빈 시간 축을 확인. 모델별로 확인하고 하나의 페이지 검사를 전체 통과로 확대하지 않는다.
- 전달 폴더에는 최종 3파일만. 개인 원문·타이머·계정은 Git 제외. 기존 보고서를 덮어쓰거나 원본을 자동 삭제하지 않는다.

## 개발 검증

```sh
python3 -m pip install -r requirements-report.txt
python3 -m unittest discover -s tests -v
node --test tests/browser.test.mjs
```

`test_portable`은 프로세스를 새로 띄워도 시간→원장→그래프 데이터 연결이 유지되는지 검사한다. 모의 테스트 통과를 실제 사이트 40회 성공이나 새 사용자 계정 재현 성공으로 표현하지 않는다.
